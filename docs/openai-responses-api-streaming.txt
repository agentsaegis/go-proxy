===========================================================================
1. WIRE FORMAT - Key Difference from Chat Completions API
===========================================================================

Chat Completions API (what stream_oai.go currently handles):
  - Uses ONLY "data:" lines (no "event:" lines)
  - Event type is embedded inside the JSON payload in choices[].delta
  - Terminates with "data: [DONE]"

  Example:
    data: {"id":"chatcmpl-xxx","choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"id":"call_abc","function":{"name":"shell","arguments":""}}]},"finish_reason":null}]}

    data: {"id":"chatcmpl-xxx","choices":[{"index":0,"delta":{"tool_calls":[{"index":0,"function":{"arguments":"{\"command\":"}}]},"finish_reason":null}]}

    data: {"id":"chatcmpl-xxx","choices":[{"index":0,"delta":{},"finish_reason":"tool_calls"}]}

    data: [DONE]


Responses API (new format):
  - Uses BOTH "event:" and "data:" lines (proper SSE)
  - Event type is on its own "event:" line, separate from the JSON payload
  - Each SSE message is: event line, data line, blank line
  - Does NOT use "data: [DONE]" - uses "response.completed" event instead

  Example:
    event: response.created
    data: {"type":"response.created","response":{"id":"resp_001","status":"in_progress",...}}

    event: response.output_item.added
    data: {"type":"response.output_item.added","output_index":0,"item":{"type":"function_call","id":"fc_001","call_id":"call_abc","name":"get_weather","arguments":"","status":"in_progress"}}

    event: response.function_call_arguments.delta
    data: {"type":"response.function_call_arguments.delta","item_id":"fc_001","output_index":0,"call_id":"call_abc","delta":"{\"lo"}

    ...more deltas...

    event: response.completed
    data: {"type":"response.completed","response":{...full response object...}}


===========================================================================
2. COMPLETE EVENT SEQUENCE FOR A FUNCTION CALL
===========================================================================

When the model generates a function call, events arrive in this order:

  1. response.created           - Response object created
  2. response.in_progress       - Response generation started
  3. response.output_item.added - Function call item appears (contains name, call_id)
  4. response.function_call_arguments.delta  (repeated N times - argument chunks)
  5. response.function_call_arguments.done   - Final arguments string
  6. response.output_item.done  - Complete function call item
  7. response.completed         - Full response with usage stats

For multiple parallel function calls, events 3-6 repeat for each call
(possibly interleaved).


===========================================================================
3. EVENT SCHEMAS - Function Call Events
===========================================================================

--- 3a. response.created ---

Emitted once when the response is first created.

  event: response.created
  data: {
    "type": "response.created",
    "response": {
      "id": "resp_001",
      "object": "response",
      "status": "in_progress",
      "output": [],
      "usage": null,
      ...
    }
  }


--- 3b. response.in_progress ---

Emitted when response generation begins.

  event: response.in_progress
  data: {
    "type": "response.in_progress",
    "response": {
      "id": "resp_001",
      "status": "in_progress",
      ...
    }
  }


--- 3c. response.output_item.added ---
(THIS IS WHERE THE FUNCTION NAME AND CALL_ID APPEAR)

Emitted when a new output item is added. For function calls, the item
has type "function_call" and contains the function name and call_id.

  event: response.output_item.added
  data: {
    "type": "response.output_item.added",
    "output_index": 0,
    "item": {
      "type": "function_call",
      "id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
      "call_id": "call_Co8dkB8h7NcTYq9dGnol",
      "name": "get_weather",
      "arguments": "",
      "status": "in_progress"
    }
  }

Fields:
  - type (string): Always "response.output_item.added"
  - output_index (int): Index of this item in the response's output array
  - item.type (string): "function_call" for function calls
  - item.id (string): Unique item ID (e.g., "fc_67d2e3cc...")
  - item.call_id (string): The call ID used to submit function output later
  - item.name (string): The function/tool name (e.g., "get_weather")
  - item.arguments (string): Empty string initially (filled via deltas)
  - item.status (string): "in_progress"

NOTE: item.id and item.call_id are DIFFERENT identifiers.
  - item.id is the output item identifier
  - item.call_id is what you use when submitting function_call_output


--- 3d. response.function_call_arguments.delta ---
(ARGUMENT CHUNKS - APPEND TO BUFFER)

Emitted repeatedly as the model generates function arguments incrementally.
The delta field contains a raw JSON string fragment - do NOT parse until done.

  event: response.function_call_arguments.delta
  data: {
    "type": "response.function_call_arguments.delta",
    "item_id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
    "output_index": 0,
    "call_id": "call_Co8dkB8h7NcTYq9dGnol",
    "delta": "{\"lo",
    "sequence_number": 42
  }

Another delta:

  event: response.function_call_arguments.delta
  data: {
    "type": "response.function_call_arguments.delta",
    "item_id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
    "output_index": 0,
    "call_id": "call_Co8dkB8h7NcTYq9dGnol",
    "delta": "cation\":",
    "sequence_number": 43
  }

Fields:
  - type (string): Always "response.function_call_arguments.delta"
  - item_id (string): Matches item.id from output_item.added
  - output_index (int): Index of this item in the output array
  - call_id (string): Matches item.call_id from output_item.added
  - delta (string): Raw JSON fragment to append to arguments buffer
  - sequence_number (int): Monotonically increasing event sequence number


--- 3e. response.function_call_arguments.done ---
(ARGUMENTS COMPLETE - AUTHORITATIVE FINAL VALUE)

Emitted once when all argument deltas have been sent. Contains the complete
arguments string. This is the authoritative value - use this, not the
accumulated deltas, for the final arguments.

  event: response.function_call_arguments.done
  data: {
    "type": "response.function_call_arguments.done",
    "item_id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
    "output_index": 0,
    "call_id": "call_Co8dkB8h7NcTYq9dGnol",
    "name": "get_weather",
    "arguments": "{\"location\":\"San Francisco\"}",
    "sequence_number": 50
  }

Fields:
  - type (string): Always "response.function_call_arguments.done"
  - item_id (string): Matches item.id from output_item.added
  - output_index (int): Index of this item in the output array
  - call_id (string): Matches item.call_id
  - name (string): Function name (NOTE: may be null due to SDK bug #2723/#573)
  - arguments (string): Complete JSON-encoded arguments string
  - sequence_number (int): Event sequence number

KNOWN BUG: The "name" field may be null in some API versions/SDKs.
See: https://github.com/openai/openai-python/issues/2723
     https://github.com/openai/openai-go/issues/573
Always get the name from response.output_item.added as the reliable source.


--- 3f. response.output_item.done ---
(COMPLETE FUNCTION CALL ITEM)

Emitted when the output item is fully generated. Contains the complete
function call object with all fields populated.

  event: response.output_item.done
  data: {
    "type": "response.output_item.done",
    "output_index": 0,
    "item": {
      "type": "function_call",
      "id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
      "call_id": "call_Co8dkB8h7NcTYq9dGnol",
      "name": "get_weather",
      "arguments": "{\"location\":\"San Francisco\"}",
      "status": "completed"
    }
  }

Fields:
  - type (string): Always "response.output_item.done"
  - output_index (int): Index of this item in the output array
  - item (object): Complete function call item with status "completed"


--- 3g. response.completed ---
(RESPONSE FINISHED - CONTAINS USAGE)

Emitted once when the entire response is done. Contains the full response
object including usage statistics.

  event: response.completed
  data: {
    "type": "response.completed",
    "response": {
      "id": "resp_001",
      "object": "response",
      "status": "completed",
      "output": [
        {
          "type": "function_call",
          "id": "fc_67d2e3ccdee0819188bf879ce5393b760b3361b29ca82d",
          "call_id": "call_Co8dkB8h7NcTYq9dGnol",
          "name": "get_weather",
          "arguments": "{\"location\":\"San Francisco\"}",
          "status": "completed"
        }
      ],
      "usage": {
        "input_tokens": 50,
        "output_tokens": 20,
        "total_tokens": 70,
        "output_tokens_details": {
          "reasoning_tokens": 0
        }
      }
    }
  }

5. COMPARISON: Chat Completions vs Responses API Streaming
===========================================================================

+-----------------------------+---------------------------------+-----------------------------------+
| Aspect                      | Chat Completions API            | Responses API                     |
+-----------------------------+---------------------------------+-----------------------------------+
| SSE format                  | data: only                      | event: + data: lines              |
| Event typing                | Inside JSON (choices[].delta)   | Separate "event:" line + "type"   |
|                             |                                 | field in JSON                     |
| Stream terminator           | data: [DONE]                    | response.completed event          |
| Tool call start             | delta.tool_calls[].id +         | response.output_item.added with   |
|                             | delta.tool_calls[].function.name| item.type="function_call"         |
| Argument streaming          | delta.tool_calls[].function     | response.function_call_arguments  |
|                             |   .arguments (string fragment)  |   .delta (string fragment)        |
| Arguments complete signal   | finish_reason: "tool_calls"     | response.function_call_arguments  |
|                             |                                 |   .done                           |
| Tool call ID field          | delta.tool_calls[].id           | item.call_id                      |
| Tool call index             | delta.tool_calls[].index        | output_index                      |
| Multiple tool calls         | Multiplexed via tool_calls[]    | Separate event sequences per item |
|                             | index field in same chunk       |                                   |
| Finish signal               | finish_reason: "tool_calls" or  | response.output_item.done per     |
|                             | "stop"                          | item + response.completed         |
| Complete item on finish     | Not provided in stream          | response.output_item.done has     |
|                             |                                 | full item                         |
| Response-level completion   | data: [DONE]                    | response.completed with usage     |
+-----------------------------+---------------------------------+-----------------------------------+

6. SUBMITTING FUNCTION OUTPUT (for context)
===========================================================================

After receiving a function call from the stream, submit the result with:

  POST /v1/responses
  {
    "model": "gpt-4o",
    "previous_response_id": "resp_abc123",
    "input": [
      {
        "type": "function_call_output",
        "call_id": "call_xyz789",
        "output": "{\"temperature\":\"15\",\"unit\":\"celsius\"}"
      }
    ]
  }

NOTE: Use "call_id" (not "id"/"item_id") to correlate function output
with the function call.


===========================================================================
7. OTHER TOOL TYPES IN RESPONSES API
===========================================================================

The Responses API also has streaming events for other tool types:

Custom tools (user-defined, non-function):
  - response.output_item.added       (item.type = "custom_tool_call")
  - response.custom_tool_call_input.delta
  - response.custom_tool_call_input.done
  - response.output_item.done

MCP tools:
  - response.output_item.added       (item.type = "mcp_call")
  - response.mcp_call_arguments.delta
  - response.mcp_call_arguments.done
  - response.mcp_call.in_progress
  - response.mcp_call.completed
  - response.mcp_call.failed

Built-in tools:
  - response.file_search_call.in_progress / .searching / .completed
  - response.web_search_call.in_progress / .searching / .completed
  - response.code_interpreter_call.in_progress / .interpreting / .completed
  - response.image_generation_call.in_progress / .generating / .completed

8. IMPLEMENTATION NOTES FOR PROXY INTERCEPTION
===========================================================================

To intercept Responses API function calls in a MITM proxy (like AgentsAegis):

1. PARSE: Split SSE stream on blank lines. Each message has:
     - "event: <type>" line
     - "data: <json>" line
   Parse the "event:" line to get the event type, then parse the JSON.

2. DETECT: Look for event type "response.output_item.added" where
   item.type == "function_call" and item.name matches a shell tool name.
   Record the item.id, item.call_id, and output_index.

3. BUFFER: Buffer all events for the tracked function call:
   - The output_item.added event
   - All function_call_arguments.delta events (accumulate delta strings)
   - The function_call_arguments.done event
   - The output_item.done event

4. DECIDE: After receiving function_call_arguments.done (or output_item.done),
   parse the accumulated arguments JSON, extract the command, and decide
   whether to inject a trap.

5. INJECT: If injecting, rebuild the buffered events with modified arguments:
   - Keep output_item.added unchanged (name stays the same)
   - Rebuild delta events with new argument chunks
   - Modify function_call_arguments.done with new arguments
   - Modify output_item.done with new arguments
   - Modify the function_call in response.completed output array

6. EMIT: Flush modified (or original) events to the client.

7. KEY DIFFERENCE FROM CHAT COMPLETIONS:
   - Must handle "event:" lines (not just "data:" lines)
   - Event type is on its own line, not inside the JSON
   - No "data: [DONE]" sentinel - use response.completed instead
   - Each function call has its own dedicated event sequence
   - call_id is a separate field (not inside choices[].delta.tool_calls[])
