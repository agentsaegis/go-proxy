  "aegis-trap-nonexistent" prefix. These use "agentsaegis/" which is a REAL

CONCERN 2: WINDOWS PATH COMPATIBILITY
------------------------------------------------------------------------------

All traps use /tmp/.aegis-sb/ which is a Linux/macOS path.

On Windows, PowerShell interprets /tmp/.aegis-sb/ as:
  - Drive-root-relative: C:\tmp\.aegis-sb\ (or whatever the current drive is)
  - This path also won't exist on Windows

VERDICT: The Linux path convention is SAFE on Windows because:
  1. C:\tmp\.aegis-sb\ won't exist either
  2. Commands fail with "path not found" on both platforms
  3. The primary safety mechanism for Windows traps is the fake domain
     ('aegis-trap.local' or DC=aegis-trap,DC=local), not the file path

However, stdout redirects like "> /tmp/.aegis-sb/file.log" will fail on
Windows, which means command output goes to terminal instead. This does
NOT affect safety (the command's side effects are the concern, not stdout).

CONCERN 3: DOWNLOAD-AND-EXECUTE PATTERNS
------------------------------------------------------------------------------

Only ONE template downloads and executes external content:
  - windows-exfiltration/iex-iwr-download-execute.yml (DISABLED)

All three commands in this file download scripts from artifact-zone.com
or networkwarmup.com and execute them via IEX/Invoke-Expression.

WHAT HAPPENS IF THESE URLs SERVE MALICIOUS CONTENT:
  - The content executes with the current user's full privileges
  - On a standard workstation: user-level access compromise
  - On a server/DC: potential domain compromise
  - The payload runs in-memory, leaving minimal forensic traces

CURRENT PROTECTIONS:
  1. Template is disabled (enabled: false)
  2. ValidateTrapSafety catches IEX + remote download pattern
  3. Both checks must be bypassed for this to be loaded

ASSESSMENT: Adequate protection exists, but the template should still be
deleted from the codebase. Its mere existence is a risk if someone modifies
the validation logic or manually enables the template.

CONCERN 4: SUPPLY CHAIN PACKAGE NAMING - MOST CRITICAL FINDING
------------------------------------------------------------------------------

Three ENABLED templates use package names under the "agentsaegis" org:

  github-install.yml:
    - npm install github:agentsaegis/env-loader
    - pip install git+https://github.com/agentsaegis/deploy-utils.git

  typosquat-npm.yml:
    - npm install @agentsaegis/env-loader
    - npm install @agentsaegis/deploy-utils
    - npm install @agentsaegis/config-sync

  typosquat-pip.yml:
    - pip install agentsaegis-env-loader
    - pip install agentsaegis-config-sync

VULNERABILITY: If any of these package/repo names are registered on their
respective registries (npm, PyPI, GitHub), the trap command will successfully
install the package and execute its install scripts.

  - GitHub repos: require agentsaegis org access (controlled, lower risk)
  - npm @agentsaegis scope: requires npm org ownership (needs verification)
  - PyPI packages: ANYONE can register these names (highest risk)

The CLAUDE.md convention says to use "aegis-trap-nonexistent" prefix, but
the safety validation EXPLICITLY ALLOWS "agentsaegis-" and "@agentsaegis/"
(templates.go line 271-273). This means the validation was intentionally
loosened to permit these names.

RISK SCENARIO:
  1. Attacker registers "agentsaegis-env-loader" on PyPI
  2. Package contains setup.py with malicious code
  3. Developer runs Claude Code, proxy injects trap:
     "pip install agentsaegis-env-loader"
  4. Hook fails to block (the scenario we're auditing for)
  5. pip installs the package, setup.py executes
  6. Attacker has code execution on developer's machine

This is NOT hypothetical - PyPI package squatting is a well-documented
attack vector and this exact pattern is commonly exploited.

------------------------------------------------------------------------------
CONCERN 5: SAFETY VALIDATION GAPS (in templates.go ValidateTrapSafety)
------------------------------------------------------------------------------

The ValidateTrapSafety function has these gaps that could allow future
unsafe traps to pass validation:

GAP 1: No check for PowerShell Invoke-WebRequest/Invoke-RestMethod domains
  The curl/nc domain check only validates Unix curl and nc commands.
  PowerShell commands using Invoke-WebRequest can target ANY domain.
  Current traps use approved domains, but validation doesn't enforce this.

GAP 2: No check for PowerShell Remove-Item path
  The rm check only validates Unix rm commands. PowerShell's Remove-Item
  is not validated. A trap using Remove-Item -Path C:\Windows\System32
  would pass validation.

GAP 3: No check for Remove-GPO domain
  The AD object removal check covers Remove-ADObject/ADUser/
  ADOrganizationalUnit but not Remove-GPO. A trap targeting a real domain
  with Remove-GPO would pass validation.

GAP 4: No check for --privileged flag on docker run
  The docker check validates image source (ghcr.io/agentsaegis/) and
  volume mounts, but does not reject --privileged or --cap-add=ALL.

GAP 5: Supply chain packages use squattable names
  The validation explicitly allows "agentsaegis-" and "@agentsaegis/"
  prefixes for package installs, but these names can be registered by
  anyone on PyPI and potentially on npm.
